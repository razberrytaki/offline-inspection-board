# 오프라인 현장 점검 보드

직원이 통신이 끊긴 현장에서 설비 점검을 완료하고, 연결이 돌아오면 감독자가 새로고침 없이 결과를 확인하는 포트폴리오 프로젝트다. 응답이 유실되어도 같은 점검은 한 건만 접수되어야 한다.

## 확정한 제품 동작

- **설비 선택** — 온라인일 때 현장 설비 목록을 기기에 저장한다. 현장에서는 저장된 목록을 설비명이나 번호로 검색해 선택한다. 목록 갱신은 IndexedDB 트랜잭션 하나로 전체를 교체한다. 내려받다 끊기면 이전 목록이 그대로 남는다.
- **점검 양식** — 설비 한 대에 대해 직원이 종합 결과를 ‘정상’ 또는 ‘이상’으로 기록한다. ‘이상’이면 메모가 필수다. 같은 설비를 다시 점검하면 새로운 점검이다. 완료한 점검의 내용은 기기에서도 바꿀 수 없고, 정정으로만 고친다.
- **정정** — 최초 작성자만 완료된 점검을 정정할 수 있다. 원본을 보존하고 새 ID를 가진 정정 기록을 만든다. 모든 정정은 원본을 가리키고, 기기가 `revision` 번호를 붙인다. 원본은 0, 첫 정정은 1, 다음 정정은 2다. 현재 결과는 revision이 가장 큰 기록이다. 감독자는 한 행에서 현재 결과를 보고 상세 화면에서 이력을 확인한다. 서버가 로그인한 사용자와 원본 작성자가 일치하는지 검사한다.
- **여러 기기의 정정 충돌** — 서버는 원본과 revision의 조합을 한 번만 받는다. 두 기기가 같은 원본에 같은 revision을 보내면 늦게 도착한 쪽이 409를 받는다. 서버는 revision n-1이 없으면 revision n을 받지 않는다. 기기는 같은 원본의 기록을 revision 순서대로 전송한다.
- **보드 정렬** — 최근 서버 접수순으로 표시한다. 뒤늦게 동기화된 점검도 처음 접수된 시점에 목록 상단에 나타난다. 정정이 처음 접수되면 기존 행을 위로 올린다. 단순 재전송은 행 수와 순서에 영향을 주지 않는다. 현장 점검 시각과 서버 접수 시각은 따로 보존한다.
- **계정과 공용 기기** — 미리 넣어 둔 데모 계정만 쓴다. 직원 2명과 감독자 1명이다. 회원가입은 없다. 기기는 기록마다 작성자를 저장하고, 현재 로그인한 사용자의 기록만 전송한다. 다른 직원이 같은 기기에 로그인해도 남의 기록이 그 직원 이름으로 접수되지 않는다. 세션 유효 기간은 근무 한 번보다 길게 잡는다.

## 동기화 API

백엔드는 Go, 프론트엔드는 Svelte를 사용한다. 직원 기기가 점검 ID를 생성하고, 첫 전송 전에 ID와 확정된 내용을 함께 저장한다. 앱을 다시 열거나 통신이 복구되면 같은 ID와 내용으로 건별 전송한다. Safari에는 Background Sync가 없으므로 앱이 닫혀 있는 동안의 전송은 약속하지 않는다.

| PUT /inspections/{id} 처리 상황 | 서버 응답 | 직원 화면 |
|---|---|---|
| 새 ID를 처음 저장함 | 저장을 확정한 뒤 201 Created와 점검 ID, 접수 시각 반환 | 동기화 완료 |
| 같은 ID와 같은 내용이 이미 저장됨 | 200 OK와 기존 ID 및 최초 접수 시각 반환 | 동기화 완료 |
| 같은 ID에 다른 내용이나 다른 작성자가 도착함 | 원본을 보존하고 409 Conflict 반환 | 로컬 기록을 유지하고 ‘확인 필요’ 표시 |
| 같은 원본의 같은 revision이 이미 있음, 또는 앞선 revision이 없음 | 409 Conflict 반환 | ‘확인 필요’ |
| 세션 만료 | 401 Unauthorized 반환 | ‘다시 로그인 필요’. 대기 기록을 유지하고 로그인 후 자동으로 다시 보냄 |
| 남의 원본을 정정함 | 403 Forbidden 반환 | ‘확인 필요’ |
| 모르는 설비, ‘이상’인데 메모 없음 등 유효성 실패 | 422 Unprocessable Content 반환 | ‘확인 필요’ |
| 응답 유실, 5xx, 429 | 기기에서 서버의 저장 여부를 확정할 수 없음 | ‘전송 대기’를 유지하고 지수 백오프로 같은 요청 재시도 |

기기는 네트워크 오류, 5xx, 429일 때만 재시도한다. 나머지 4xx는 재시도하지 않는다.

서버는 설비 ID, 결과, 메모, 점검 시각, 작성자, 원본 ID, revision으로 동일성을 판정한다. 기기는 재시도할 때 처음 저장한 요청 본문을 그대로 보내므로 정규화는 서버만 한다. 서버는 메모를 NFC로 정규화하고 앞뒤 공백을 제거한 뒤, 정규화한 필드의 SHA-256 값을 `content_hash`로 저장하고 이 값으로 비교한다.

요청 본문의 형식은 다음과 같다. 점검 시각은 UTC 밀리초 정수다. 원본은 `rootId`가 경로의 ID와 같고 `revision`이 0이다. 작성자는 본문에 없고 서버가 세션에서 정한다.

```json
{
	"rootId": "0193a1c2-...",
	"revision": 0,
	"equipmentId": "P-12",
	"result": "abnormal",
	"memo": "가동 중 누수 발견",
	"inspectedAt": 1764130000000
}
```

201과 200의 응답 본문은 `{"id": "...", "receivedAt": "..."}`다. 409의 응답 본문은 `reason`에 `content_mismatch`, `revision_taken`, `missing_previous` 중 하나를 담는다. `content_mismatch`이고 요청자가 저장된 기록의 작성자일 때는 그 기록도 함께 담아 ‘확인 필요’ 화면이 나란히 보여줄 수 있게 한다.

동시에 같은 요청이 들어와도 한 건만 생성하며, 중복 요청으로 새 접수 알림을 만들지 않는다. 정정 ID에도 같은 재시도 규칙을 적용한다.

## 데이터 모델

```sql
create table inspections (
	id            uuid primary key,
	root_id       uuid not null references inspections(id),
	revision      int  not null,
	equipment_id  text not null references equipment(id),
	result        text not null check (result in ('normal', 'abnormal')),
	memo          text not null default '',
	inspected_at  timestamptz not null,
	author_id     text not null,
	content_hash  bytea not null,
	received_at   timestamptz not null default now(),
	unique (root_id, revision)
);
```

- `id`는 기기가 만든다. 원본은 `root_id`가 자기 `id`이고 `revision`이 0이다.
- `inspected_at`은 기기 시계, `received_at`은 서버 시계다. `author_id`는 요청 본문이 아니라 세션에서 가져온다.
- 설비는 삭제하지 않고 폐기 플래그만 둔다. 오프라인 기기가 폐기된 설비를 점검해도 서버가 받는다.
- 보드는 `DISTINCT ON (root_id) ... ORDER BY root_id, revision DESC`로 원본마다 최신 기록을 고르고, 그 기록의 `received_at` 내림차순으로 정렬한다. revision n은 n-1보다 늦게 접수되므로 최신 기록의 접수 시각이 그 행의 최근 접수 시각이다. 재전송은 행을 만들지 않으므로 순서를 바꾸지 않는다.

PUT 처리는 트랜잭션 하나에서 먼저 ID로 기존 기록을 찾고, 있으면 `content_hash`를 비교해 200 또는 409를 보낸다. 새 ID는 설비와 정정 요건을 확인한 뒤 `INSERT ... ON CONFLICT DO NOTHING RETURNING received_at`으로 저장한다. 행이 반환되면 201을 보내고 알림을 만든다. 행이 반환되지 않으면 ID로 다시 조회해 `content_hash`를 비교한다. 같은 ID가 없으면 `revision_taken`으로 409를 보낸다. 알림은 커밋이 성공한 뒤에만 Go 프로세스 안의 브로드캐스터로 보낸다. 서버 프로세스는 하나로 둔다. 여러 인스턴스가 필요해지면 Postgres `LISTEN/NOTIFY`로 바꾼다.

## 직원 기기의 기록 상태

기기의 기록 하나는 다음 상태 중 하나다.

- `pending` — 기기에 저장했고 서버 접수를 확인하지 못했다. 화면에는 ‘전송 대기’로 표시한다.
- `sending` — 요청을 보내는 중이다. 이 상태는 저장하지 않는다. 전송 중에 앱이 종료되면 다시 열 때 `pending`으로 보고 같은 요청을 보낸다.
- `synced` — 201이나 200을 받았다. 화면에는 ‘동기화 완료’로 표시한다.
- `needs_attention` — 409, 403, 422를 받았다. 화면에는 ‘확인 필요’로 표시한다.
- `needs_login` — 401을 받았다. 로그인하면 `pending`으로 돌아간다.

‘확인 필요’ 상세 화면은 서버 기록과 로컬 기록을 나란히 보여준다. 동작은 두 가지다. ‘새 점검으로 다시 제출’은 같은 내용을 새 ID로 만든다. ‘이 기기에서 삭제’는 로컬 기록을 지운다.

## 제안한 구현과 화면 구성

- **저장과 전송** — Go의 net/http, pgx, PostgreSQL을 사용한다. 프론트엔드는 SvelteKit을 adapter-static으로 빌드하고 Go 바이너리에 `go:embed`로 넣는다. 서비스 워커는 SvelteKit의 `$service-worker` 모듈로 빌드 파일을 미리 받아 두고 오프라인에서 화면을 다시 연다. IndexedDB는 `idb` 래퍼로 다루며 설비 목록과 기록을 보관한다.
- **기기 저장소 보존** — 첫 실행에 `navigator.storage.persist()`를 요청한다. iOS Safari는 홈 화면에 추가하지 않은 사이트의 저장소를 7일 동안 방문이 없으면 지울 수 있다. 요청이 거절되면 경고와 ‘홈 화면에 추가’ 안내를 표시한다.
- **HTTPS** — 서비스 워커와 `crypto.randomUUID()`는 HTTPS나 localhost에서만 동작한다. 실제 휴대폰으로 데모하려면 HTTPS 터널이나 mkcert 인증서를 쓴다.
- **현장 점검** — 연결 상태, 저장된 설비 수, 마지막 목록 갱신 시각, 전송 대기 건수를 보여준다. 연결 상태는 `navigator.onLine`이 아니라 마지막 요청의 성공 여부로 판단한다. 설비를 선택한 뒤 결과와 메모를 입력한다. 기기 저장 직후와 서버 접수 후의 상태를 구분한다.
- **내 기록** — 직원이 전송 대기 및 확인 필요 기록을 찾아보고, 상세 화면에서 본인이 작성한 점검을 정정한다.
- **감독자 보드** — 서버가 접수한 점검의 설비, 현재 결과, 메모, 작성자, 점검 시각, 최근 접수 시각을 표시한다. 전체·이상 필터는 현재 결과를 기준으로 한다. 저장 확정 후 SSE로 변경을 알린다. 휴대폰에만 있는 전송 대기 수는 직원 화면에서 표시한다.
- **보드 재연결** — 보드는 SSE를 먼저 연결해 이벤트를 쌓아 두고, 서버 목록을 조회한 뒤, 쌓인 이벤트를 적용한다. 이벤트는 `root_id` 기준으로 덮어쓰고 더 큰 revision만 반영한다. 같은 이벤트를 두 번 적용해도 결과가 같다.
- **장애 패널** — 데모 빌드에만 켜는 화면이다. 오프라인 전환, 저장 직후 응답 끊기, 중복 전송 버튼과 요청 로그, 서버 행 수를 함께 보여준다. 리뷰어가 ‘한 건만 접수된다’는 보장을 직접 확인한다.

## 하지 않는 것

첫 데모는 다음 기능을 만들지 않는다.

- 사진 첨부
- 설비별 체크리스트 항목
- 여러 현장
- 설비 관리 화면
- 감독자의 기록 수정과 삭제
- 회원가입
- 앱이 닫혀 있는 동안의 백그라운드 전송

## 첫 데모의 인수 기준

1. 온라인에서 설비 목록을 받은 직원이 오프라인에서 ‘P-12 냉각수 펌프’를 찾아 ‘이상’과 ‘가동 중 누수 발견’을 기록한다. 앱을 닫았다 다시 열어도 기록이 전송 대기로 남는다.
2. 연결 복구 후 서버가 점검을 저장한 직후 응답을 끊는다. 재시도하면 기기에 동기화 완료가 표시되고, 감독자 보드에는 새로고침 없이 점검 한 건만 나타난다.
3. 최초 작성자가 메모를 정정하면 원본을 보존한 채 보드의 기존 행이 맨 위로 이동한다. 같은 정정을 재전송해도 이력과 접수 시각이 그대로 유지된다.

## 검증 방법

- 세 인수 기준은 Playwright E2E 테스트로 자동화한다. 오프라인은 `context.setOffline()`으로 만든다.
- 2번 기준의 응답 끊기는 개발 모드 전용 Go 미들웨어로 만든다. 토글이 켜져 있으면 커밋 후 `http.Hijacker`로 연결을 닫는다. 장애 패널도 같은 미들웨어를 쓴다.
- 동시성은 Go 테스트로 검증한다. 같은 PUT 50개를 동시에 보내고 행 1개와 알림 1개를 확인한다.
